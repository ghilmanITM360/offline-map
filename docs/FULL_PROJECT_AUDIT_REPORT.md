# Full Project Audit Report

Consolidated cross-check of all `docs/*.md` against the current working-tree code state (branch `codex/ijtema-map-data-v2`, 2026-07-19). This report reads every doc under `docs/`, verifies each claim against the actual source (file/line citations below), and calls out where docs are stale, aspirational, contradicted by code, or — the opposite direction — where code has quietly moved *ahead* of what the docs still describe as "planning only."

Methodology: read all 21 pre-existing `docs/*.md` files in full; cross-checked specific claims with `grep`/`Read` against `src/`, `scripts/`, `android/`, `ios/`; ran `npm run typecheck` (clean) and spot-checked 3 representative test scripts (`test-entry-gate-routing`, `test-outside-street-graph-integration-v2`, `test-v1-v2-isolation` — all pass) rather than the full 86-script suite, given time budget. Also read root `PROJECT_AUDIT.md` (a prior, independent audit dated the same day) and reconciled its findings against current code, since several of its findings have since been fixed by later work.

**Single most important structural finding, stated up front**: almost the entire feature set described in `docs/MAP_EXPERIENCE_REDESIGN_REPORT.md` (11 phases) and the entire outside-venue OSM street-graph routing system (`docs/OFFLINE_OUTSIDE_ROUTING_FINAL_SPEC.md` → `docs/OSM_DATA_VALIDATION_REPORT.md` → `docs/RUNTIME_NAVIGATION_FINAL_REPORT.md`) is real, present, and working in the current working tree — but **none of it is committed to git**. `git status` shows dozens of new/modified files as untracked (`??`) or modified-but-unstaged (`M`), including the entire street-graph dataset (`src/data/ijtema/streetGraph.ts`, 512KB), the routing engine upgrade (`src/utils/MinHeap.ts`, `src/services/OutsideStreetRoutingService.ts`), all new map-layer components (`src/views/components/map/*.tsx`), and the Jest/RNTL component-test suite (`src/__tests__/*.test.tsx`). If this working tree were lost, essentially all work described as "done" in the last two weeks of docs would be lost with it. See Risk Areas.

## Partially Completed Features

- **Outside street-graph routing ships default-OFF and is architecturally split from the older gate-selection path** — `RoutingServiceV2.selectOutsidePath` (fast, A*/street-graph-aware) is used for actual `outside_coordinate` route calculation, but `EntryGateRoutingService.findBestGateForOutsideUser`/`resolveRouteStartForUser` (slow, unheaped O(V²) `dijkstraCost`, `EntryGateRoutingService.ts:76-110`) remains live and is still called from `HomeViewModel.ts:48` (`getHomeSnappedCoordinate`, triggered on every Recenter tap while outside the venue). This second implementation was **not** upgraded to A*/MinHeap even though the sibling `RoutingServiceV2.calculateShortestPath` was — see Conflicting Implementations below. In practice this runs against the small 289-node internal venue graph (not the 7,945-node street graph), so the runtime cost is modest, not the "hundreds of ms to seconds" the implementation plan warned about for the street-graph case — but it is genuinely dead/duplicate logic relative to the now-superior `selectOutsidePath` gate-selection.

- **Jest/RNTL component tests exist but cover only 3 screens** (`DirectionsScreen`, `HomeScreen`, `NavigationScreen`) out of ~14 screens `docs/FULL_UI_COMPONENT_AUDIT.md` enumerates, and none of `Settings`, `AppGuide`, `Drawer`, `Permission`, `Splash`, `DownloadMap`, `Error`. This closes part of the "zero UI tests" gap the root `PROJECT_AUDIT.md` flagged, but not all of it, and the remaining `readFileSync`-string-match "tests" (`test-home-buttons-v2.ts` etc., still ~35 of the 86 scripts per the same PROJECT_AUDIT.md methodology, not re-counted here) still masquerade as UI verification in `npm test`'s naming.

## Conflicting Implementations

1. **Two independent, redundant "best outside gate" selectors, now with diverging performance characteristics.** `RoutingServiceV2.selectOutsidePath` (fast: `findBestPath` over a binary-heap A*, plus the new street-graph path) computes the actual route used for outside-venue navigation. `EntryGateRoutingService.findBestGateForOutsideUser`/`resolveRouteStartForUser` (slow: unheaped O(V²) `dijkstraCost`, `EntryGateRoutingService.ts:76-110, 215-258`) is a **separate, still-live** implementation of the same "minimize approach + internal cost" policy, called from `HomeViewModel.ts:48` for the Home screen's snapped-location display on every Recenter tap. Both `docs/OFFLINE_OUTSIDE_ROUTING_IMPLEMENTATION_PLAN.md` §4 and root `PROJECT_AUDIT.md` §4 flagged this exact duplication as pre-existing tech debt and recommended *not* fixing it in that pass, scoping it as a follow-up de-duplication — that follow-up has still not happened, and the two implementations have since diverged further in performance profile (one got the A* upgrade, the other didn't), which is new since those docs were written.

2. **`resolveStartCandidates`'s `outside_coordinate` branch in `RoutingServiceV2.ts` is dead code.** `resolveStartCandidates` (`RoutingServiceV2.ts:205-250`) has an `outside_coordinate` branch (lines 238-250) that calls `EntryGateRoutingService.resolveRouteStartForUser` — but `resolveStartCandidates` is called from exactly one place, `selectDefaultPath` (line 699), and `selectDefaultPath` is never invoked for `outside_coordinate` starts (`calculateRoute`'s dispatch ternary at lines 733-735 always routes `outside_coordinate` to `selectOutsidePath` instead). This specific branch is unreachable for its apparent purpose. `docs/OFFLINE_OUTSIDE_ROUTING_IMPLEMENTATION_PLAN.md` §4 noted `selectDefaultPath` "does NOT handle outside_coordinate starts (guarded out at dispatch)" but did not flag that this makes the corresponding branch in its own upstream caller (`resolveStartCandidates`) dead.

3. **`docs/ARCHITECTURE_CLEANUP_ROADMAP.md`'s explicitly-flagged zoom-threshold bug was fixed by unrelated work, silently, exactly the way the roadmap said not to.** The roadmap (§3, dated 2026-07-18) says: "**Do not silently 'fix' this by picking one value during constants consolidation** — surface it as a decision point." The redesign session (`docs/MAP_EXPERIENCE_REDESIGN_REPORT.md`, task #26/#27, same day or after) extracted `GateLayer.tsx` and, as a side effect of importing the shared `MEDIUM_ZOOM`/`HIGH_ZOOM` constants, resolved the `14` vs `15` mismatch to `15` without any dedicated product decision or on-device QA of that specific visual change being called out. The outcome may well be correct, but it happened via a different, unreviewed path than the one the roadmap explicitly asked for — worth a retroactive confirmation this was noticed and accepted, not just inherited.

4. **Four independent `pointInPolygon` implementations remain unconsolidated**, confirmed still present exactly where `docs/ARCHITECTURE_CLEANUP_ROADMAP.md` §2a and root `PROJECT_AUDIT.md` §4 describe: `RoutingService.ts:51`, `SnapToRoadService.ts:163`, `graphBuilder.ts:298`, `EntryGateRoutingService.ts:112`. No `GeoUtils.ts` exists (confirmed via `find`). Similarly, `distanceMeters` remains duplicated between `graphBuilder.ts:71` (exported, canonical) and a private copy in `entryPolicy.ts:59` — both still present, unconsolidated, exactly as flagged.

5. **`docs/PRODUCTION_RUNTIME_QA_PLAN.md` (dated 2026-07-18) and `docs/MAP_EXPERIENCE_REDESIGN_REPORT.md`'s embedded QA sessions (2026-07-19) partially overlap but were not written with awareness of each other** — the Production Runtime QA Plan's Section B ("re-verification surface for `2fa3fec`") and Section C (re-verification surface for `2298b04`) predate the street-graph and map-redesign work entirely; none of its ~40 checklist rows have been re-run against current `HEAD`, and the redesign report's own on-device sessions used a different, narrower ad-hoc checklist rather than executing the Production Runtime QA Plan's rows. There is no single current source of truth for "which QA rows are actually verified against current HEAD" — a tester would need to manually reconcile at least four documents (`PRODUCTION_RUNTIME_QA_PLAN.md`, `V2_FULL_APP_EMULATOR_QA_TEST_CASES.md`, `RUNTIME_QA_FINAL_REPORT.md`, `RUNTIME_NAVIGATION_FINAL_REPORT.md`, plus the redesign report's QA appendix) to know current coverage.

6. **Five "planning only, no code changed" docs are now stale in a way that could mislead a future reader.** `docs/OFFLINE_OUTSIDE_ROUTING_FINAL_SPEC.md`, `docs/OFFLINE_OUTSIDE_ROUTING_IMPLEMENTATION_PLAN.md`, `docs/OUTSIDE_ROUTING_ARCHITECTURE_DECISION.md`, `docs/OUTSIDE_TO_INSIDE_NAVIGATION_AUDIT.md`, and `docs/OSM_DATA_VALIDATION_REPORT.md` each open with a status line asserting no code was modified / implementation is pending approval. All five predate `docs/RUNTIME_NAVIGATION_FINAL_REPORT.md`, which documents the resulting feature working on-device. ## Risk Areas

- **Nearly all recent work is uncommitted.** `git status` at audit time shows the entire street-graph subsystem, the entire map-experience-redesign component set, the Jest/RNTL test suite, and most of `docs/` itself as untracked (`??`) or modified-unstaged (`M`) against the last real commit (`2298b04`). This includes a 512KB generated data file (`streetGraph.ts`) and dozens of new source/test files. **There is no commit boundary protecting this work** — a `git clean`/`git checkout .`/failed rebase/lost machine would silently destroy weeks of implementation and QA work with no recovery path from git history. This is the single highest-leverage housekeeping risk in the repo right now, independent of any code-quality finding above.
- **Live, un-rotated leaked Google Maps API key** (`docs/SECURITY_AUDIT.md` C1) — reconfirmed still present and live in local `.env` this pass. Anyone who mined the key from git history before commit `a7833f7` has a working credential today.
- **Release Android builds still fall back to debug signing** unless a developer has locally created `android/keystore.properties` (which does not exist by default, only `.example`) — confirmed no such file present. Any release APK built today, unless someone has already configured this locally, is debug-signed, undermining the Maps-key SHA-1 restriction plan (C1/C3 interaction) and not distributable to Play Store as-is.
- **`RUNTIME_NAVIGATION_FINAL_REPORT.md` and `RUNTIME_QA_FINAL_REPORT.md` are genuinely on-device evidence, not source-level claims** — this is worth stating positively, since the task brief asked to be skeptical of "FINAL"-named reports. Both explicitly used a real AVD, captured screenshots (paths listed), reported BLOCKED rows honestly instead of glossing over them, and their PASS claims are consistent with what the code actually does when spot-checked here. The skepticism should instead be aimed at the **absence of equivalent on-device evidence for Phases 5-11 of the map redesign** (rasta endpoints, LOD, controls, outside-banner copy, selected-block contrast, bilingual search, satellite dimming) and **all of iOS** — those are the parts of the current feature set that are verified only by typecheck/lint/script tests, exactly the pattern `CLAUDE.md`'s "Runtime status" section and the Production Runtime QA Plan warn about.
- **`npm test`'s 86-script chain was not executed in full during this audit** (time budget; 3 representative scripts spot-checked and passed, plus a clean `npm run typecheck`). Given the volume of uncommitted change since the last documented full run, a full `npm test` pass should be re-confirmed before any further claims are layered on top of this report.
- **No CI pipeline exists** (`.github/workflows/` confirmed empty, per `docs/SECURITY_AUDIT.md`) — nothing automatically enforces `test:map-config` (secret-scanning) or the typecheck/lint/test gates before a commit or merge. Combined with the uncommitted-work risk above, there is currently no automated safety net at any stage between "code written" and "code shipped."
- **Outside-gate-selection duplication (Conflicting Implementations #1)** is low-urgency today (runs against a small 289-node graph) but is exactly the kind of "two implementations quietly diverge" risk the project has already been bitten by once (`RASTA_06_OUT_OF_ORDER_POINTS`, per `docs/RUNTIME_QA_FINAL_REPORT.md`'s GIS Validation section) — worth scheduling the de-duplication `docs/ARCHITECTURE_CLEANUP_ROADMAP.md` and the implementation plan both already recommended, before it diverges further.
- **QA-document fragmentation** (Conflicting Implementations #5) makes it easy to double-count or miss coverage — a future contributor asking "has X been verified on-device" currently has to cross-reference five separate documents with inconsistent row-naming and no shared status ledger.
