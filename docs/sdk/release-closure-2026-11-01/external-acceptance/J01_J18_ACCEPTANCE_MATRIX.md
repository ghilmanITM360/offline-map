## Before any physical run

1. Confirm named tester/observer, device-owner consent and safe venue permission. Use a stationary operator or walking companion; stop on unsafe instructions. Do not change device settings without consent. Record model, OS/build, battery/low-power state, locale/theme/text scale, location precision, screen-reader version/voice and real-versus-mock status.
2. Copy [the result template](ACCEPTANCE_RECORD.template.json) into a per-platform/per-build/per-scenario record. Fill the full source, S1/D1/L1, binary SHA-256, app id/version/build, signing public fingerprint and native manifest identities. Verify the installed app corresponds to the artifact. “Latest build” is insufficient. Do not install an iOS simulator executable on a phone or use an original-Ijtema application checklist as if it were this SDK consumer.
3. Prefer the approved physical target; do not rebuild because an emulator checklist exists. If the target or required observation/control does not exist, record BLOCKED with the exact missing item. J07/J15 require separately approved QA targets and synthetic labels. Never add production instrumentation, mocks, fault hooks or privileged settings under this documentation task.
4. Confirm current pack ids/pins using the identity packet. Karachi manifest: `e248c3730203c7535d82041f665ed41809edfe7998959bbe10f6ee9390a03ad1`; synthetic manifest: `edd5367bf0bdf1ca4eebba68a69c6ff177eb7d8ccf865593560ae76bcb11f7b0`. Never treat the synthetic venue as a real walking route. Imported/remote packs remain refused.
5. Establish how timestamp-only native observations, watcher ownership and pending-result state will be captured without location leakage. A moving dot alone cannot prove one watcher or zero post-Exit callbacks. If the approved build cannot expose required evidence, keep that subcase BLOCKED and request a scoped observability decision; do not infer PASS from screen behavior.

## Real GPS walking procedure — J01/J02 and relevant subcases

1. At an owner-approved, surveyed open-sky start in the actual covered venue, confirm no mock/simulator source. Record current permission state; create a Manual Guide first. Route ids and destination must resolve to the current venue. This consumer must not be expected to supply the absent outside street provider.
2. Request Live explicitly, observe candidate and confirm with fresh precise authorization. Record the first native timestamp, cadence and active watcher count. Do not accept cached location or numeric accuracy as proof of authorization.
3. Walk the approved route for 10 minutes, including pauses and real turns. Record new fix timestamps, progress and visible instructions. Record actual cadence/gaps; the original plan requires continuous updates, not an invented universal sampling interval. If signal is lost, progress must freeze honestly and recover only on a newer observation.
4. For J06, while stationary disable location/services for >8 seconds, then restore. Observe lost/recovered states and timestamps. Airplane mode is a network condition, not a reliable GPS-loss mechanism. For J10 use a safe pre-approved deviation; provider outage injection requires the actual host/approved control.
5. Observe arrival at the real destination. On Android inspect the Arrival Card/Done control at 100% and 200% text, with gesture and three-button navigation where supported; it must be visible/reachable above system bars. Record unsupported navigation variants as blocked coverage rather than a pass.
6. Exit; observe zero SDK-owned watchers/callbacks/progress after cleanup and no old-result resurrection when a new route starts. Record the observation interval and trace. Execute the original J03–J13 substeps separately, including 20 J12 cycles and held-result races; this ten-minute walk alone does not close them.

## Whole-device offline cold-launch procedure — J14

1. Establish two independent cycles on a dedicated consented test device: **empty-install/uninitialized app storage** and **previously initialized warm storage**. Install the approved app while permitted, but do not first open the empty-install cycle or inject pack files. If reinstall/reset requires erasing personal data, stop and arrange a dedicated device instead. Keep evidence of the pre-launch state.
2. Stop/terminate the app; enable whole-device Airplane Mode in Settings. Explicitly turn off Wi-Fi, cellular connectivity, Bluetooth and any tethered network route; disconnect the debug/network cable where feasible. Record the actual settings. Apple permits radios to be re-enabled in airplane mode, so the airplane icon alone is insufficient ([Apple instructions](https://support.apple.com/en-us/108785)).
3. Launch from the home screen with no Metro/dev server or network asset injection. Record startup, bundled pack/map, OSM notice, pan/zoom, directory/search, destination/origin selection and Manual Guide Next/Previous/Exit. Observe for five minutes. Capture native file/network evidence if available; inability to trace every request must be stated rather than claiming zero packets. A mandatory fetch/dead end is FAIL.
4. Repeat after initialized storage with a terminated process. Record GPS availability honestly; satellite acquisition may differ offline, and Manual Guide must remain usable. A JS `EXPO_OFFLINE` export or simulator HTTP denial is not this test.
5. If the distribution/provisioning mechanism itself requires online activation, document and resolve that prerequisite before the offline first-launch cycle; do not silently warm application assets to hide a first-launch dependency. Restore the owner's settings afterward.

## VoiceOver / TalkBack procedure — J16, combined with J17

1. Experienced tester enables actual VoiceOver in iPhone Settings → Accessibility → VoiceOver, or TalkBack in Android Settings → Accessibility → TalkBack, with owner consent. Confirm speech is audible and record reader/voice/OS versions and language. Apple describes swiping between controls and double-tapping to activate in [its VoiceOver guidance](https://developer.apple.com/documentation/uikit/supporting-voiceover-in-your-app); Google supplies [TalkBack setup](https://support.google.com/accessibility/android/answer/6007100) and [gestures](https://support.google.com/accessibility/android/answer/6151827). Download any needed voice beforehand and separately record offline availability.
2. At ordinary and largest supported text, traverse directory/search/results, origin/destination, preview, Manual Next/Previous/Exit, Live candidate/confirm/cancel, Recenter, GPS banners, reroute, Arrival/Done and dialogs. Record spoken labels/roles/state and exact focus order. All critical controls must be reachable without visual targeting or a focus trap.
3. With a stationary observer/safe companion, induce actual lost/recovered GPS, reroute, a new instruction, arrival and Exit. Record event time, actual spoken text and number of announcements. Critical state changes must be audible once without repeated/overlapping floods; verify focus remains sensible after transitions and modal dismissal. A screen reader reading a focused banner is not proof that an unsolicited safety change was announced.
4. Repeat English and separately reviewed Urdu/Roman Urdu. Record mixed-script fallback, pronunciation, RTL reading order and physical map orientation; do not approve untranslated English as reviewed Urdu. Test largest text/light/dark and narrow phones. Android live font changes have documented activity recreation: record loss honestly; a requirement for preserved journey needs a separate owner product decision.
5. Retain consented screen/audio recording or an approved external recording when OS capture omits speech; confirm playback includes the reader. No SDK turn-by-turn speech feature is claimed: screen-reader accessibility and the SDK's lack of standalone voice guidance are distinct. Mark unavailable voices, missing copy or unobservable audio BLOCKED/FAIL as appropriate, never PASS from an accessibility tree.
