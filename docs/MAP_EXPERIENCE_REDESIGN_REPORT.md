# Map Experience Redesign Report

Progress log for the Google-Maps-style redesign. See `docs/MAP_EXPERIENCE_AUDIT.md` for the pre-work architecture audit and risk ranking that this sequencing follows.

## Completed

### Foundation (reordered ahead of Phase 1 per audit risk ranking)

- **Shared map-layer components** (`src/views/components/map/{BlockLayer,GateLayer,RastaLayer,SpecialRouteLayer,VenueBoundary}.tsx`, `mapLayerStyles.ts`): de-duplicated the block/gate/rasta/special-route Polygon/Marker/Polyline JSX that was copy-pasted (and already drifting) between HomeScreen and NavigationScreen. Each component takes a `variant: 'home' | 'nav'` prop to preserve the two screens' distinct visual treatment exactly as before — pure extraction, no UX change.
- **Unified zoom-threshold system**: `V2MapRenderingService`'s `LOW_ZOOM/MEDIUM_ZOOM/HIGH_ZOOM/DEFAULT_ZOOM` constants are now exported and reused by `GateLayer`'s home-variant label LOD (previously a second, divergent 14/16.5 threshold hardcoded inline in HomeScreen). `src/utils/mapZoom.ts` centralizes the region→zoom estimation formula, previously duplicated. NavigationScreenV2 (now folded into Home, see below) was also wired to pass real camera zoom into `getHomeLayers()` instead of always defaulting to 15.
- **Single persistent MapView instance** — the core structural fix: Home, NavigationScreenV1, and (the old) NavigationScreenV2 each owned an independent `MapView` + `mapRef`, and exiting navigation called `navigation.reset()`, destroying and remounting Home's map every time. Fixed by:
  - `useNavigationOverlayV2` (`src/viewmodels/useNavigationOverlayV2.ts`): wraps `useNavigationViewModelV2` plus camera-follow/fit-to-route/back-handler effects, designed to run inside HomeScreen against Home's own `mapRef` instead of a separate screen's map.
  - `NavigationMapLayersV2` (map children: route polylines, start/dest/user markers, nav-variant block/gate/rasta layers) and `NavigationChromeV2` (instruction card, trip bar, recenter, arrival modal) — rendered by HomeScreen when `isNavigating` and the v2 nav flag are on, replacing Home's browse chrome instead of pushing a new screen.
  - `NavigationViewModelV2.handleExit` now just calls `stopNavigation()` — no more stack reset. The two v2 "start navigation" call sites (`HomeScreen.handleStartPreviewNavigation`, `DirectionsViewModel.handleStartNavigation`) no longer push/navigate to a `Navigation` screen; the Directions entry point calls `navigation.goBack()` to reveal the already-mounted Home underneath.
  - `NavigationScreen.tsx`'s old `NavigationScreenV2` component (~360 lines) was deleted as dead code — it's no longer reachable through any navigation call site. `NavigationScreen` now only renders the legacy v1 path, plus `NavigationScreenV2Disabled` as a defensive fallback if a v2 route ever lands there unexpectedly (e.g. a stale deep link).
  - Scope: this consolidation is v2-only. `NavigationScreenV1` and legacy v1 map data are untouched, per `CLAUDE.md`'s "v1 is a rollback/dev fallback kept alive for legacy tests" guidance.

## Phase 1: Directions folded into a persistent-map sheet (task #29)

`DirectionsScreen` is no longer a pushed stack screen — it is now a plain component (`src/views/screens/DirectionsScreen.tsx`, same file/export name to keep the existing test-script surface stable) that takes `{ destination, onClose }` props and renders as alternate content inside Home's existing `<BottomSheet>`, swapped in whenever `HomeScreen`'s new `directionsDestination` state is set, instead of the selected-place panel.

- `RootNavigator`'s `Directions` route and the `Directions: { destination: Place }` param type are removed entirely — there is no longer a stack entry to navigate to.
- `HomeScreen.handleOpenDirections` (tapping "Directions" from a place sheet) and `handleChangePreviewStart` (tapping "Change Start" from the route preview card) now call `setDirectionsDestination(...)` + `bottomSheetRef.current?.snapToIndex(1)` instead of `nav.navigate('Directions', ...)`.
- Inside the sheet, `DirectionsScreen`'s header-back button, "Change destination" link, and "Show route on map" button all now call the same `onClose` prop (`HomeScreen.handleCloseDirections`, which just clears `directionsDestination`) — this mirrors the pre-refactor behavior exactly, since all three previously called the identical `navigation.goBack()`.
- `DirectionsScreen` swapped its internal `ScrollView` for `@gorhom/bottom-sheet`'s `BottomSheetScrollView` (so pan/keyboard gestures coordinate correctly with the host sheet) and dropped `SafeAreaView`/`useSafeAreaInsets` (not meaningful inside a partial-height sheet). The existing `KeyboardAvoidingView` + `keyboardShouldPersistTaps`/`keyboardDismissMode` props were kept as-is. Home's `<BottomSheet>` gained `keyboardBehavior="interactive"`, `keyboardBlurBehavior="restore"`, `android_keyboardInputMode="adjustResize"` so the manual-start search `TextInput` behaves correctly now that a sheet (not a full screen) hosts it.
- Home's existing `activePreviewRoute` auto-close effect (which collapses the sheet once a v2 route is ready) is now guarded with `&& !directionsDestination`, so it no longer races the directions sheet closed out from under the user while they're still choosing a start point.
- **Consolidated the two redundant start-navigation code paths** the phase was scoped to fix: `DirectionsViewModel.handleStartNavigation` was dead code (defined, returned from the hook, but never called from any JSX — confirmed via repo-wide grep) ever since commit `a7833f7` removed its only call site and replaced it with the Home route-preview card's `handleStartPreviewNavigation`. Deleted it, along with its now-unused `NativeStackNavigationProp`/`RootStackParamList`/`RoutePointService`/`startNavigation` imports and destructures. `HomeScreen.handleStartPreviewNavigation` is now the single production start-navigation path for v2, and it gained the flag/destination validation (`V2NavigationAdapter.canStartActiveNavigation`, surfaced via `Alert.alert` on failure) that the dead code used to be responsible for but that nothing was actually enforcing at the real call site.

## Phase 6 (task #33): zoom-based visibility (LOD) polish

The unified threshold system (task #27, `LOW_ZOOM=13/MEDIUM_ZOOM=15/HIGH_ZOOM=16.5`) already gated every layer's *labels* by zoom (`visibleBlockLabels`, `visibleGateMarkers`, `visibleRastaLabels`, `visibleSpecialRouteLabels`), and gate *markers* themselves were reduced to majors-only below `MEDIUM_ZOOM`. The gap: block polygons and rasta polylines had no equivalent — `getHomeLayers().blocks`/`.rastas` rendered all 42 blocks and all 11 rastas at every zoom level, so a fully zoomed-out view was as visually dense as a fully zoomed-in one. This is the concrete part of the task's literal spec ("low zoom = boundary/major gates/major routes only; medium = blocks/gates/rastas; high = all labels/small routes/details") that wasn't yet true.

- `V2MapRenderingService.getHomeLayers()`: added two new fields, `visibleBlocks`/`visibleRastas` — below `MEDIUM_ZOOM` they collapse to "selected item only" (empty if nothing selected), matching the existing gate low-zoom-majors-only precedent; at/above `MEDIUM_ZOOM` (or when the user has explicitly picked the "Blocks"/"Rastas" filter chip, bypassing LOD same as labels already did) they're the full set. The pre-existing `blocks`/`rastas` fields are untouched (still always full) — `HomeScreen.tsx` now renders `visibleBlocks`/`visibleRastas` instead, while `NavigationMapLayersV2` (active-navigation overlay) deliberately keeps consuming the raw, unfiltered `blocks`/`rastas`, consistent with the established "nav mode shows full context, no LOD" pattern already true for its gate/special-route layers.
- Simplified `visibleRastaLabels`: its old bespoke `zoomLevel < LOW_ZOOM` branch (hide all but selected) is now redundant since its input (`visibleRastas`) is already reduced that way below `MEDIUM_ZOOM` — replaced with a plain `pickByZoom(visibleRastas, ...)` call, same output, less special-casing.
- Special routes (Shahr-e-Pindal) and majors-only gates were already correctly treated as the "major gates/major routes" that stay visible at low zoom — no change needed there; this phase only had to close the blocks/rastas gap.
- New test: `scripts/test-map-geometry-lod-v2.ts` (`npm run test:map-geometry-lod-v2`, wired into `npm test`) — asserts low/medium/high zoom counts for `visibleBlocks`/`visibleRastas`, that a selection stays visible even zoomed out, that the explicit filter-chip bypass works, that the raw `blocks`/`rastas` fields stay full regardless of zoom, and that `NavigationMapLayersV2` still sources from the raw fields (not the new zoom-gated ones).
- Verified: `npm run typecheck` clean, `npm run lint` clean (same one pre-existing unrelated warning), full `npm test` (63 scripts, exit 0) green, `npm run test:components` (25 tests, 3 suites) green. One pre-existing literal-source-string test (`scripts/test-home-controls.ts`) asserted the exact old `blocks={showBlockPolygons ? v2MapLayers.blocks : []}` JSX string — updated to the new `visibleBlocks`/`visibleRastas` prop expressions, same pattern as every other JSX-relocation fix logged in this report's "Test suite maintenance" section.
- Not yet done: Android on-device confirmation of how the low-zoom collapse actually feels in practice — whether hiding all blocks/rastas below `MEDIUM_ZOOM` (until the user zooms in or selects something) reads as "helpfully decluttered" or "map looks empty," which is a UX judgment call that needs a real device/emulator pass, not just the count assertions above.

## Phase 7 (task #34): map controls redesign

Two separate problems under one task: (1) the Compass+Zoom(+Layers) button cluster was hand-rolled twice — once for browse mode's `rightControls`, once for the nav-overlay's `navControls` — using the same styles but fully duplicated JSX; (2) the top-right controls' vertical position (`rightControlsTop`) was a chain of hardcoded per-banner height guesses (`42`/`56`/`60`) stacked on top of each other, which silently goes wrong the moment a banner's real rendered height differs from the guess (longer warning text wrapping to 2 lines, larger system font scaling, etc.) — same problem for the recenter button's clearance above the route-preview card (`184`, also a guess).

- New `src/views/components/map/MapControls.tsx`: one shared component (`variant: 'browse' | 'nav'`) rendering the Compass + Zoom pair, with the Layers button and the "North-up/Free rotate" helper badge gated to browse mode only (unchanged behavior — nav mode never had a Layers button). `HomeScreen.tsx`'s two independent JSX blocks now both render `<MapControls variant="browse" .../>` / `<MapControls variant="nav" .../>` with the same handlers as before. Purely presentational — the caller still owns absolute positioning, since browse anchors this cluster at the top and nav anchors it at the bottom (a deliberate Phase 2 decision, kept as-is — nav's top is occupied by the instruction card).
- New `src/views/components/map/mapControlStyles.ts`: the 7 button styles (`controlButton`, `controlButtonActive`, `controlHelperBadge`, `controlHelperText`, `zoomControls`, `zoomButton`, `zoomDivider`) moved out of `HomeScreen.tsx`'s local `StyleSheet` (values unchanged, pixel-identical) since they're now shared.
- Real layout fix: `rightControlsTop` and `rightControlsBottom` (browse mode only) now derive from `onLayout`-measured heights (`bannerStackHeight`, `routePreviewCardMeasuredHeight`) instead of hardcoded guesses. The three top banners (offline pill, map-warning, outside-venue) were converted from three independently `position: 'absolute'`-positioned elements with individually guessed `top` values into flow children of one measured `bannerStack` container — `rightControlsTop` now reads that container's actual rendered height, so it stays correct even if banner text wraps differently than assumed. Same treatment for the route-preview card's height feeding the recenter button's clearance.
- Scope decision — **left untouched**: `NavigationChromeV2`'s own recenter-button bottom offset (`Math.max(insets.bottom,12)+140`, a guess for the trip bar's height) and `navControls`' bottom offset (`...+12+140+56+16`, stacking above that same guess). Both are hardcoded-guess patterns of the same kind fixed above, but fixing them requires coordinating a shared height measurement across two different components/files (`NavigationChromeV2` owns the trip bar, `HomeScreen` owns `navControls`), and — unlike the browse-mode banners — this exact positioning was explicitly confirmed working on-device in the 2026-07-19 QA retry logged above. ## Phase 11 (task #38): satellite mode with legible overlays

Unlike Phases 5/8/9/10, this one really was a new capability, not a fix hiding behind a stale task description — the audit is explicit that "no overlay-contrast system exists today" (§6/§7, risk #9). Satellite toggle itself already existed (`toggleMapType`/`settings.mapMode`, the Layers action sheet's "Switch to Satellite" option, an offline guard that blocks it without connectivity) — what was missing is that every block/gate/rasta/route/label color was tuned once, for the flat gray/white standard basemap, and never adjusted for satellite imagery, which is visually busy and varies wildly in color by location.

- Considered re-tuning every layer's per-state color/opacity specifically for satellite (a second color variant per component), but rejected it: it would mean guessing new colors for ~15 different fill/stroke/text combinations with no way to see the actual satellite imagery at this venue's coordinates, i.e., high risk of guessing wrong in ways that are worse than doing nothing, and no way to verify without a device.
- Instead: new `src/views/components/map/SatelliteDimOverlay.tsx` — a single semi-transparent dark scrim (`rgba(0,0,0,0.32)`, `zIndex: -1`, non-tappable) rendered directly above the satellite tiles and below every existing overlay (venue boundary at `zIndex: 0` and up). Every block/gate/rasta/label/route keeps its exact current colors and gets more legible "for free" against the now-darkened imagery underneath — a uniform, low-risk fix instead of ~15 individual guesses.
- `HomeScreen.tsx`: renders the scrim only when satellite tiles are the actually-rendered basemap (`mapType === 'satellite' && hasGoogleMapsKey && !isOffline` — deliberately mirrors the exact condition the `<MapView mapType=...>` prop itself already resolves through, so the scrim can't show over the graph-only/`'none'` fallback if the user picked satellite before going offline, which would just needlessly darken a basemap that isn't there). New static `SATELLITE_DIM_BOUNDARY` covers the venue bounds padded 50% outward (so gates and their approach streets just outside the venue are covered too, not only the interior), following the existing `VENUE_BOUNDARY` static-constant pattern already in this file.
- New test: `scripts/test-satellite-dim-overlay-v2.ts` (`npm run test:satellite-dim-overlay-v2`, wired into `npm test`) — asserts the scrim component exists with correct z-ordering and non-tappability, that `HomeScreen` renders it, and specifically that its visibility condition matches the MapView's own resolved-basemap logic (the offline/satellite interaction above) rather than the raw preference alone.
- Verified: `npm run typecheck` clean, `npm run lint` clean (same one pre-existing unrelated warning), full `npm test` (68 scripts, exit 0) green, `npm run test:components` (25 tests, 3 suites) green.
- **Not yet done — most speculative "not yet done" of this session**: the `0.32` opacity value was picked by reasoning about typical satellite-imagery brightness, not measured against this venue's actual tiles. Whether it's enough to make blocks/labels pop, or so much it makes the imagery pointless to show at all, can only be judged by actually looking at satellite mode over this venue on a device — more so than any other phase's "not yet done," this number should be treated as a first guess to be tuned after a real look, not a validated default.

## Final (task #39): performance pass, verification, closing summary

### Performance pass

Went through the task's literal checklist — "memoized markers, viewport rendering, clustering if needed for 42 blocks/17 gates/11 rastas/3 pindals without FPS drops":

- **Marker memoization (`tracksViewChanges`)**: audited every `<Marker>` across `BlockLayer`/`GateLayer`/`RastaLayer`/`SpecialRouteLayer`/`HomeScreen`/`NavigationMapLayersV2`. Found and fixed a real gap: the three live-navigation markers (route start pin, destination pin, snapped-user-location pulse in `NavigationMapLayersV2.tsx`) had no `tracksViewChanges` prop at all, silently defaulting to react-native-maps' `true` — continuous re-snapshotting for the entire duration of every navigation session, the most performance-sensitive screen in the app. Fixed the start/destination pins to `tracksViewChanges={false}` (static content, no reason to re-render). The user-location pulse marker uses a continuous `Animated.View` ring animation — rather than guess whether disabling tracksViewChanges would freeze that animation, checked for precedent first: `HomeScreen.tsx`'s browse-mode current-location marker uses the *identical* pulse technique and already has `tracksViewChanges={false}`, so the nav-mode marker was brought in line with that established, presumably-already-validated pattern rather than left as an unexplained inconsistency. This inference (matching existing precedent) is not itself a fresh on-device confirmation that the pulse still animates correctly — flagged below.
  - Everything else was already correctly memoized: every label/dot/badge marker across all four shared layer components explicitly sets `tracksViewChanges={false}`, and `GateLayer`'s home-variant markers use a bounded 400ms `transitioning` window (from earlier work, predating this session) instead of a permanent `true`/`false`, to avoid thrashing during LOD-tier label transitions.
  - Extended `scripts/test-marker-performance-v2.ts` (already an existing, dedicated test for exactly this class of bug) with the three newly-fixed nav markers, so this can't silently regress.
- **Viewport rendering**: the zoom-based LOD system (task #27, extended in task #33/Phase 6 this session) already limits what's actually drawn — below `MEDIUM_ZOOM`, block polygons and rasta polylines collapse to "selected only," and gates collapse to majors-only, so a zoomed-out view never renders the full 42+17+11+3 set simultaneously. This is a coarser mechanism than true viewport-bounds culling (it's zoom-level-based, not camera-bounds-based), but for a single fixed-size venue (not an unbounded map), zoom level is a reasonable proxy for "is the user looking at the whole venue or a part of it."
- **Clustering**: not implemented, and judged unnecessary — ~73 total entities (42+17+11+3) is well below the scale (typically hundreds to thousands of markers) where `react-native-maps` marker clustering earns its complexity and dependency cost, especially with the LOD system already thinning the low-zoom case. Adding a clustering library here would be speculative complexity with no observed FPS problem driving it, which cuts against this project's stated anti-scope-creep guidance. If a real on-device FPS drop is ever observed at this entity count, that would be the trigger to revisit, not this pass.
